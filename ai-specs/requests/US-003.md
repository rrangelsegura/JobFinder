## Original

# US-003 - Candidate Authentication

## User Story

**As a** job seeker,

**I want** to create an account and log in to JobFinder,

**So that** the platform knows who I am across visits, and my CV, analysis results, chat history, and action plan are mine and nobody else's.

## Business Value

- Unblocks US-002 (Candidate Workspace) — the dashboard and CV upload cannot safely resolve a real `candidateId` without this.
- Establishes the identity boundary every future candidate-facing capability (chat, analysis results, action plan, and anything after) depends on.
- Protects candidate data (CV contents, personal info, career plans) from being visible to or overwritten by the wrong person.

## Scope of This Story

- **Registration**: a job seeker can create an account with email + password.
- **Login**: a job seeker can authenticate with email + password and receive a session.
- **Session persistence**: the session survives a page reload / new tab, not just the initial login moment.
- **Logout**: a job seeker can end their session.
- **Route protection**: US-002's dashboard (and any future authenticated route) refuses to load for an unauthenticated visitor and redirects to login instead.

## Open Design Questions (not resolved by this story — for design.md when this becomes a change)

- **Where do credentials live?** `docs/data-model.md`'s `Candidate` entity currently has no password/credential fields, and there's no separate `User`/`Account` entity in the data model. Two options: (a) add credential fields directly to `Candidate`, or (b) introduce a distinct auth entity that `Candidate` relates to. This affects how cleanly auth stays separable from profile data long-term.
- **Session mechanism**: JWT (stateless, no server-side lookup) vs. server-side session backed by Redis (already in the stack for BullMQ, so no new infra dependency either way). Affects logout semantics (a JWT can't be easily revoked before expiry; a Redis-backed session can be deleted immediately).
- **Password storage**: standard practice is a salted hash (e.g., bcrypt/argon2) — not actually "open" as a decision, but must be explicit in design.md and not left to implementation-time improvisation.

## Acceptance Criteria

- A new job seeker can register with an email and password; a duplicate email is rejected with a clear error (mirrors `Candidate.email`'s existing `@unique` constraint).
- A registered job seeker can log in with correct credentials and reach the workspace (US-002).
- Incorrect credentials are rejected with a generic error that does not reveal whether the email exists (standard practice — avoids account enumeration).
- The session persists across a page reload without requiring the candidate to log in again.
- A logged-in candidate can log out, after which the workspace (US-002) is no longer reachable without logging in again.
- Passwords are never stored or logged in plain text.
- Attempting to reach US-002's workspace (or any future authenticated route) while unauthenticated redirects to login instead of loading candidate data.

## Out of Scope

- Password reset / "forgot password" flow.
- Social/OAuth login (Google, LinkedIn, etc.).
- Multi-factor authentication.
- Email verification on signup.
- Account deletion or profile-level permission granularity (e.g., roles) — only "authenticated candidate" vs. "not authenticated" exists at this stage.
- Company-side (`Employee`) authentication — this story is candidate-only; `Employee` login (for interviewers) is a separate concern if/when that side of the product is built.

## Priority

High — blocking prerequisite for US-002 and every subsequent candidate-facing story.

## Enhanced

# US-003 - Candidate Authentication

## User Story

**As a** job seeker,

**I want** to create an account and log in to JobFinder,

**So that** the platform knows who I am across visits, and my CV, analysis results, chat history, and action plan are mine and nobody else's.

## Functional Description

This story resolves its own three "Open Design Questions" with concrete, justified decisions — per Spec Driven Development, these must not be left to implementation-time improvisation:

1. **Credentials live directly on `Candidate`** (not a separate `User`/`Account` entity). `Candidate` is currently the only authenticated actor type in the data model; `Employee` auth is explicitly out of scope, and introducing a shared identity entity now — for a system with exactly one actor type — is premature abstraction. If/when `Employee` auth is built, that is the right moment to decide whether to extract a shared base. Add a single new field: `Candidate.passwordHash` (String).
2. **Server-side session backed by Redis**, not JWT. Redis is already running in this stack for BullMQ (`infra/docker-compose.yml`), so this adds no new infrastructure. The deciding factor is logout semantics: the acceptance criteria require that logout immediately ends the session — a Redis-backed session is deleted server-side and is instantly unusable, whereas a JWT remains valid until expiry unless a revocation list is added (extra complexity this story doesn't need). Session id is delivered via an `httpOnly`, `secure`, `sameSite=lax` cookie — never exposed to JS/localStorage, which also closes off XSS-based token theft. `frontend/src/stores/authStore.ts` (from US-002) holds only derived client state (`isAuthenticated`, `email`), never the session id itself.
3. **Password hashing: bcrypt**, cost factor 12. Widely supported in the Node ecosystem, no native build complexity beyond what's already normal for this stack.

### Processing flow

1. **Register**: `POST /auth/register` `{ email, password }` → validate email format + password ≥ 8 chars → hash password (bcrypt) → `Candidate.create` (or reject on unique-email conflict) → do **not** auto-login; candidate proceeds to log in explicitly (keeps register/login as two clearly separable, testable flows).
2. **Login**: `POST /auth/login` `{ email, password }` → look up `Candidate` by email → `bcrypt.compare` → on success, create a session record in Redis (`session:<sessionId> → { candidateId }`, TTL e.g. 7 days) and set the session cookie → on failure (unknown email OR wrong password), respond with the **same generic 401** either way (no "email not found" vs "wrong password" distinction — prevents account enumeration).
3. **Session check on app load**: frontend calls `GET /auth/session` on mount; `200 { candidateId, email }` populates `authStore`, `401` leaves it unauthenticated. This is what `ProtectedRoute` (US-002) actually gates on.
4. **Logout**: `POST /auth/logout` → delete the Redis session record + clear the cookie → `200`.
5. **Route protection (backend)**: a `requireAuth` Express middleware reads the session cookie, looks up Redis, and either attaches `req.candidateId` (derived server-side, never client-supplied) and calls `next()`, or responds `401`. This middleware is what US-002's flagged security issue needs: `backend/api/routes/uploads.ts`'s `POST /uploads/cv` must be updated to use `req.candidateId` from this middleware instead of `req.body.candidateId` — this story is what makes that fix possible, and the fix should ship as part of this story's Definition of Done, not be deferred again.

## Endpoints

- `POST /auth/register` — `{ email: string, password: string }` → `201 { candidateId }` / `400` (invalid email, password too short, or email already registered — this one *can* say "email already registered," registration is not subject to the same anti-enumeration concern as login, since the candidate is actively choosing that email themselves).
- `POST /auth/login` — `{ email: string, password: string }` → `200` + `Set-Cookie` (session) / `401 { error: "Invalid email or password" }` (generic, for both failure cases).
- `POST /auth/logout` — no body → `200`, clears session.
- `GET /auth/session` — no body → `200 { candidateId, email }` / `401`.

All under a new `Auth` tag in `docs/api-spec.yml`, following the same standard response envelope (`status`, `data`, `agent_trace_id`, `model_used`) used by the `Uploads` endpoints.

## Fields to Add

- `backend/api/routes/uploads.ts` — **required change**: derive `candidateId` from `req.candidateId` (via `requireAuth`) instead of `req.body.candidateId`. This directly resolves the security gap flagged during US-002's enrichment.

- [ ] `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/session` implemented per the Endpoints section, with unit tests (Jest + Supertest, following the pattern already used in `backend/api/routes/uploads.test.ts`) covering: successful register/login, duplicate email on register, wrong password on login, unknown email on login (same generic error as wrong password), session persists across a simulated reload (re-call `GET /auth/session` with the same cookie), logout invalidates the session (subsequent `GET /auth/session` returns `401`).
- [ ] `requireAuth` middleware implemented and unit tested in isolation (valid session → `next()` + `req.candidateId` set; missing/invalid/expired session → `401`).
- [ ] `backend/api/routes/uploads.ts` updated to use `requireAuth` + `req.candidateId`; existing upload tests updated to reflect the new auth requirement instead of a client-supplied `candidateId`.
- [ ] Passwords verified never logged (check any request/error logging middleware doesn't dump raw request bodies for `/auth/*`).
- [ ] Frontend: `LoginPage`, `RegisterPage`, `authStore`, session-check-on-load wired to US-002's `ProtectedRoute`.
- [ ] Manual curl verification (per this project's mandatory testing standard) against the live stack: register → login → access a protected route with the session cookie → logout → confirm the same cookie no longer works.
- [ ] `docs/api-spec.yml` and `docs/data-model.md` updated.

## Non-Functional Requirements

- **Security**: bcrypt cost factor 12; generic error on login failure (no account enumeration); `httpOnly`/`secure`/`sameSite=lax` session cookie; session TTL (e.g., 7 days) enforced in Redis; basic rate limiting on `POST /auth/login` (e.g., per-IP and/or per-email, even a simple fixed-window counter in Redis) to blunt brute-force attempts — this is new scope relative to the Original story, added because "non-functional requirements (security...)" is an explicit enrichment checklist item and login endpoints are a standard brute-force target.
- **Observability**: failed login attempts should be logged (without the attempted password) to support future rate-limiting/alerting tuning.
- **Performance**: bcrypt cost factor 12 is deliberately chosen to be slow enough to resist offline cracking but should be benchmarked on the actual deployment hardware to confirm login latency stays acceptable (not blocking for this story, but worth a note before cost factor is changed later).
