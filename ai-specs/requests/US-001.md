## Original

# US-001 - Parse Candidate CV

## User Story

**As a** job seeker,

**I want** to upload my CV in PDF format and have the system automatically extract my professional information,

**So that** I don't have to manually enter my personal, educational, and work experience data.

## Business Value

- Reduce candidate onboarding time.
- Minimize manual data entry.
- Create a structured candidate profile that can be reused by the remaining agents.

## Acceptance Criteria

- The user can upload a PDF CV.
- The system extracts the candidate's personal information.
- The system extracts work experience.
- The system extracts education.
- The system extracts technical and soft skills when available.
- The system extracts languages and certifications when present.
- The extracted information is returned in a structured format.
- The user is notified if the PDF cannot be processed.

## Out of Scope

- CV quality analysis.
- CV rewriting.
- Job matching.
- Candidate scoring.
- Career recommendations.

## Priority

High

## Enhanced

# US-001 - Parse Candidate CV

## User Story

**As a** job seeker,

**I want** to upload my CV in PDF format and have the system automatically extract my professional information,

**So that** I don't have to manually enter my personal, educational, and work experience data.

## Functional Description

The candidate uploads a CV file through the frontend. The **Node.js API Gateway** receives the file, validates it, persists a `Resume` record, and delegates the heavy-lifting (OCR + structured extraction) to the **Python Agentic Core** (`CV Analyst` agent), following the Hybrid Architecture data flow: `Frontend → Node.js API → Python Agent Core (FastAPI) → Local LLM (Ollama) → Tools/Knowledge Base → Response`.

Because OCR + LLM extraction is a long-running task, processing is **asynchronous**: the API returns immediately with a `202 Accepted` and a job/trace id, and the frontend polls (or subscribes via WebSocket) for the result, per `docs/backend-standards.md` (job queue + WebSocket/Polling requirement).

### Processing flow

1. **Upload & validation** (Node.js API Gateway)
   - Accept `multipart/form-data` on `POST /uploads/cv`.
   - Validate: file present, MIME type `application/pdf`, size ≤ 10MB (per `Resume` validation rules in `docs/data-model.md`).
   - Reject with `400` if validation fails; reject with a clear "unreadable/corrupted file" error if the PDF cannot be parsed at all.
   - Persist a `Resume` row (`filePath`, `fileType`, `uploadDate`, `candidateId`) via Prisma.
   - Enqueue an extraction job (Redis/BullMQ) and return `202` with `{ resumeId, jobId, status: "processing" }`.
2. **OCR + extraction** (Python Agentic Core, `CV Analyst` agent)
   - Run OCR (PyTesseract, fallback Amazon Textract) to obtain raw text from the PDF.
   - Prompt the local LLM (`llama3:8b` or `mistral:7b` for the extraction, per model-selection guidance) to produce **structured output validated against a Pydantic schema** (mandatory per `docs/backend-standards.md` — local models must not return free-form JSON).
   - On success, persist extracted data to the relational store (`Candidate`, `Education`, `WorkExperience`) and chunk/embed the resume text into the `resumes_embeddings` vector collection (per `docs/data-model.md` §4) tagged by section (`skills`, `experience`, etc.) for later RAG/matching use.
   - On failure (OCR failure, LLM output fails schema validation after retry), mark the job `failed` with a user-facing reason.
3. **Result retrieval** (Node.js API Gateway)
   - Frontend polls `GET /uploads/cv/{jobId}` (or subscribes via WebSocket) for `status: processing | completed | failed` and, when completed, the structured `Candidate` payload.

### Fields to extract and persist

| Field group | Fields | Target entity |
|---|---|---|
| Personal info | `firstName`, `lastName`, `email`, `phone`, `address` | `Candidate` |
| Education | `institution`, `title`, `startDate`, `endDate` (up to 3 records, per data-model constraint) | `Education` |
| Work experience | `company`, `position`, `description`, `startDate`, `endDate` | `WorkExperience` |
| Skills, languages, certifications | free-text list | **Gap — see Open Questions** |
| Resume metadata | `filePath`, `fileType`, `uploadDate`, `candidateId` | `Resume` |

> **Open question / schema gap:** the current 12-entity relational model (`docs/data-model.md`) has no `Skill`, `Language`, or `Certification` entities, yet the acceptance criteria require extracting them. Two options to resolve before implementation:
> 1. Store them as a `JSONB` field (e.g. `Candidate.extractedSkills`) for MVP, and/or
> 2. Rely on the Vector Domain (`resumes_embeddings`, `section: "skills"`) for semantic retrieval instead of structured storage.
> This decision must be made and the `data-model.md` updated (per SDD rules — spec before code) before implementation starts.

## Endpoints

Extends the existing `Uploads` tag in `docs/api-spec.yml`:

- `POST /uploads/cv` (existing — **needs behavior update**: from synchronous `201` to asynchronous `202` per the standard async pattern)
  - Request: `multipart/form-data` with `file` (PDF, ≤10MB) and `candidateId` (or created inline if candidate doesn't exist yet — to be clarified).
  - Response `202`: `{ status: "success", data: { resumeId, jobId, status: "processing" }, agent_trace_id, model_used: null }`
  - Response `400`: unsupported file type, missing file, or size exceeded.
- `GET /uploads/cv/{jobId}` (**new**)
  - Response `200`: `{ status: "success", data: { status: "processing"|"completed"|"failed", candidate?: Candidate, error?: string }, agent_trace_id, model_used }`
  - Response `404`: unknown job id.

Both responses must follow the standard envelope defined in `docs/backend-standards.md` (`status`, `data`, `agent_trace_id`, `model_used`).

## Files / Modules to Modify

Per the Hybrid Architecture boundaries (`docs/backend-standards.md`):

- `backend/prisma/schema.prisma` — confirm/add `Resume`, `Candidate`, `Education`, `WorkExperience` models and any new field for extraction status/skills.
- `backend/api/routes/uploads.ts` (Node.js) — multipart upload handling, validation, job enqueue, `GET /uploads/cv/{jobId}`.
- `backend/api/queue/` — Redis/BullMQ job producer + WebSocket/polling notification wiring.
- `backend/agents/cv_analyst/` (Python) — `CV Analyst` agent: OCR invocation + LLM-based structured extraction.
- `backend/agents/cv_analyst/schemas.py` — Pydantic schema for the extraction output (mirrors the `Candidate`/`Education`/`WorkExperience` fields above).
- `backend/knowledge_base/ocr/` — PyTesseract/Textract wrapper module.
- `backend/knowledge_base/embeddings/` — chunking + embedding pipeline into `resumes_embeddings`.
- `docs/api-spec.yml` — update `/uploads/cv` to async contract, add `GET /uploads/cv/{jobId}`.
- `docs/data-model.md` — resolve the skills/languages/certifications gap noted above.

## Non-Functional Requirements

- **Security:** validate MIME type and file size server-side (not just extension); store uploaded files outside the web root; sanitize extracted text before persistence to avoid stored-injection in downstream rendering.
- **Performance:** OCR + LLM extraction must run asynchronously and not block the request thread; target extraction completion within a defined SLA (to be benchmarked) for a typical 1–3 page CV.
- **Observability:** every extraction attempt must log an `agent_trace_id` and the `model_used`, per the standard response envelope, to support debugging non-deterministic LLM output.
- **Reliability:** on LLM structured-output validation failure, retry once with a refined prompt before marking the job `failed` (hallucination guardrail standard).
- **Data integrity:** enforce the existing `Education` (max 3 records) and field-length constraints from `docs/data-model.md` when persisting extracted data.
