## Original

# US-002 - Candidate Workspace (Dashboard Shell + CV Upload)

## User Story

**As a** job seeker,

**I want** a persistent workspace within JobFinder where I can upload my CV, and that will later also let me chat with the JobFinder agent, review my CV analysis results, and see my action plan,

**So that** I have one consistent place to manage my job-search journey instead of a one-off upload form with nothing behind it.

## Business Value

- Establishes the foundational information architecture (navigation/sections) that every future candidate-facing capability plugs into, instead of each feature shipping as a disconnected page.
- Turns the already-built CV parsing backend (US-001) into something a real candidate can actually use, not just an API callable via curl.
- Gives the candidate a durable sense of "my space" in JobFinder from their very first action, which the roadmap (chat, analysis results, action plan) builds on.

## Scope of This Story

This story delivers:
1. **A dashboard shell**: persistent layout and navigation with sections for Upload, Chat, Analysis Results, and Action Plan. Only **Upload** is functional in this story — the other three sections exist in the navigation as visible-but-not-yet-built placeholders, so the structure is established now and later stories slot in without redesigning navigation.
2. **A working CV upload section**: wraps the existing `POST /uploads/cv` / `GET /uploads/cv/{jobId}` backend contract from US-001. Given that backend is asynchronous (`202` + poll, not immediate), the UI must show upload progress, a "processing" state while the job runs, and the terminal `completed` or `failed` state — not just a fire-and-forget submit button.

## Dependency (Blocking, Not Delivered By This Story)

This story requires the candidate to be **authenticated** — the dashboard is "my" workspace, and CV upload needs a real `candidateId`, not one typed in by hand. There is currently no authentication/session mechanism anywhere in JobFinder (no login endpoint, no session handling, no password field on `Candidate`) — `docs/backend-standards.md` mentions "user authentication, session management" as a Node.js API Gateway responsibility, but it was never implemented.

**Decision:** authentication is a real prerequisite story, not something this story solves as a side effect. This story cannot start implementation until that prerequisite exists (or is explicitly stubbed by a decision made when that story is written). Suggested as the next story to define: **US-003 - Candidate Authentication**.

## Acceptance Criteria

- The candidate can access a workspace that shows a persistent navigation with (at least) four sections: Upload, Chat, Analysis Results, Action Plan.
- Chat, Analysis Results, and Action Plan are visibly present in the navigation but clearly marked as not yet available (e.g., disabled/"coming soon") — they must not look broken or dead.
- From the Upload section, the candidate can select and submit a PDF CV.
- While the extraction job is processing, the UI reflects a "processing" state (not a blank screen or a misleading "done").
- On completion, the UI reflects success and does not require a page reload or manual re-check to notice the result changed.
- On failure, the UI shows a clear, non-technical error message (not a raw stack trace or the backend's internal error string).
- The workspace only loads for an authenticated candidate; there is no path to upload a CV without an established identity.

## Out of Scope

- Chat with the JobFinder agent (functionality — the nav placeholder is in scope, the feature is not).
- Displaying CV analysis results (functionality — nav placeholder only).
- Displaying the action plan (functionality — nav placeholder only).
- Authentication/session management itself (see Dependency above — this is a separate, prerequisite story).
- Any changes to the CV parsing backend itself (US-001's upload/status/extraction contract is consumed as-is).

## Priority

High — this is the first real user-facing entry point into JobFinder; without it, US-001's backend has no way for an actual candidate to reach it.

## Enhanced

# US-002 - Candidate Workspace (Dashboard Shell + CV Upload)

## User Story

**As a** job seeker,

**I want** a persistent workspace within JobFinder where I can upload my CV, and that will later also let me chat with the JobFinder agent, review my CV analysis results, and see my action plan,

**So that** I have one consistent place to manage my job-search journey instead of a one-off upload form with nothing behind it.

## Functional Description

This story scaffolds the JobFinder **frontend** (does not exist in the repo yet) per `docs/frontend-standards.md`'s stack: **React 18 + TypeScript + Vite + React Router DOM 6+ + Tailwind + Shadcn/UI + Zustand (global state) + TanStack Query (server state / polling) + Axios (HTTP client)**.

The workspace is a protected route tree behind an auth guard fed by US-003's session. Only the Upload section calls a real backend endpoint in this story; Chat / Analysis Results / Action Plan are rendered as disabled nav items pointing at not-yet-implemented routes.

### Processing flow

1. **Route guard** (`ProtectedRoute`): reads the candidate session from a Zustand `authStore` (populated by US-003). No session → redirect to `/login`. This is a client-side UX guard only — the backend must independently enforce authentication on every request (see Security note below); the frontend guard is not a security boundary by itself.
2. **Workspace shell** (`WorkspaceLayout`): persistent sidebar/topbar with 4 nav entries. Upload is a live `<Link>`; Chat/Results/Action Plan render as disabled items (no navigation, visually marked "coming soon").
3. **Upload** (`CvUploadForm`): file input restricted to `.pdf` client-side (fast feedback only — the backend's magic-byte + size validation from US-001 remains the actual source of truth, per `specs/cv-upload/spec.md`). On submit, `POST /uploads/cv` via Axios as `multipart/form-data`.
4. **202 received** → a TanStack Query hook (`useCvExtractionStatus(jobId)`) begins polling `GET /uploads/cv/{jobId}` on a `refetchInterval` (e.g. 2500ms), stopping once `data.status` is `completed` or `failed` (TanStack Query supports conditional `refetchInterval` based on the last response — no manual `setInterval` needed).
5. **`completed`** → show a success state with a short summary from `data.candidate` (e.g. name + counts of education/experience/skills entries found) — full result display is explicitly Out of Scope (that's the future Analysis Results section), this is just upload confirmation.
6. **`failed`** → show `data.error` translated to a non-technical message (map known backend error substrings — "unreadable/corrupted", "Unsupported file type", OCR/LLM failure reasons — to friendly copy; do not render the raw string from `specs/cv-extraction/spec.md`'s failure paths directly).

### ⚠️ Security issue found while enriching this story (requires a backend change)

`POST /uploads/cv` (as built in US-001 / `parse-candidate-cv`) reads `candidateId` directly from the client-supplied multipart form field, with no verification against who is actually authenticated. That was acceptable for curl-based backend testing, but **once real users exist (US-003), this is a direct authorization bypass**: any authenticated candidate could upload a CV under a different candidate's id just by editing the form value, overwriting someone else's profile data.

**Required accompanying backend change** (small, but must ship with or before this story goes live for real users): `backend/api/routes/uploads.ts` must derive `candidateId` from the authenticated session (however US-003 implements it — JWT claim or server-side session lookup), not from `req.body.candidateId`. `docs/api-spec.yml`'s `CVUploadAcceptedResponse` request body should drop `candidateId` as a client-supplied field once this lands. Until US-003 exists, this cannot be fixed for real (there's no session to derive it from) — flagging now so it isn't missed once auth ships.

## Endpoints Consumed (no new backend endpoints; existing contract from `parse-candidate-cv`)

- `POST /uploads/cv` — `multipart/form-data`, field `file` (PDF, ≤10MB). **`candidateId` field usage must change per the Security note above once US-003 lands** — until then, this story cannot go to production with real users, only to a staging/demo environment.
  - `202`: `{ status, data: { resumeId, jobId, status: "processing" }, agent_trace_id, model_used }`
  - `400`: `{ status: "error", data: { error } }`
- `GET /uploads/cv/{jobId}`
  - `200`: `{ status, data: { status: "processing"|"completed"|"failed", candidate?, error? }, agent_trace_id, model_used }`
  - `404`: unknown job id

Both per `docs/api-spec.yml`'s `CVUploadAcceptedResponse` / `CVExtractionStatusResponse` schemas (already documented, not changing shape in this story beyond the `candidateId` note above).

## Files / Modules to Modify

New (`frontend/` doesn't exist yet — this story scaffolds it):
- `frontend/package.json`, `vite.config.ts`, `tsconfig.json`, `tailwind.config.js` — per `docs/frontend-standards.md`'s stack.
- `frontend/src/app/router.tsx` — React Router DOM route tree, `ProtectedRoute` wrapping the workspace routes.
- `frontend/src/layouts/WorkspaceLayout.tsx` — persistent nav shell (Atomic Design "Organism" per frontend-standards.md).
- `frontend/src/stores/authStore.ts` — Zustand store; **shape/contents owned by US-003**, this story only consumes it (session present/absent, no session-management logic here).
- `frontend/src/features/upload/UploadPage.tsx`, `CvUploadForm.tsx`, `useCvUpload.ts` (TanStack Query mutation), `useCvExtractionStatus.ts` (TanStack Query polling hook).
- `frontend/src/lib/apiClient.ts` — Axios instance, base URL to the Node API Gateway.
- `frontend/src/components/nav/DisabledNavItem.tsx` — for the Chat/Results/Action Plan placeholders.

Existing (conditional on the Security note above, not required to start frontend work but required before real users touch this):
- `backend/api/routes/uploads.ts` — derive `candidateId` from session instead of form field.
- `docs/api-spec.yml` — drop `candidateId` from the documented request body once the above lands.

- [ ] `frontend/` scaffolded per `docs/frontend-standards.md` (Vite + React 18 + TS strict + Tailwind + Shadcn/UI).
- [ ] `WorkspaceLayout` with 4 nav sections; only Upload is a live route.
- [ ] `ProtectedRoute` wired to US-003's `authStore`; unauthenticated access redirects to `/login`.
- [ ] Upload flow implemented end to end: file select → client-side PDF/size check → `202` → poll → `completed`/`failed` UI states, per Acceptance Criteria.
- [ ] Backend error strings mapped to non-technical UI copy (not rendered raw).
- [ ] Security note resolved or explicitly tracked as a blocking follow-up before any non-demo deployment (see above).
- [ ] Unit tests: Vitest + React Testing Library for `CvUploadForm` and `useCvExtractionStatus` (including the polling-stops-on-terminal-state behavior).
- [ ] E2E test: Playwright, "upload CV → observe processing state → observe completed state" — this exact scenario is already named as the reference example in `docs/frontend-standards.md`'s Testing Standards.
- [ ] Accessibility: keyboard-navigable nav and upload form, semantic HTML, via Shadcn/Radix primitives per `docs/frontend-standards.md`.
- [ ] Responsive: workspace usable on mobile viewport.
- [ ] `docs/api-spec.yml` updated if/when the `candidateId` contract changes (see Security note).

## Non-Functional Requirements

- **Security**: see the flagged issue above — must not ship to real users with client-supplied `candidateId`.
- **Performance**: route-based code splitting via `React.lazy` for the workspace sections, per `docs/frontend-standards.md`.
- **Accessibility**: Radix/Shadcn primitives, high color contrast, semantic HTML.
- **Observability**: not required for this story's UI, but consider surfacing `agent_trace_id` in a dev-only debug panel to ease future troubleshooting (optional, not blocking).
- **Resilience**: if the polling request itself fails (network blip, not a `failed` job status), retry transparently rather than surfacing a false failure — TanStack Query's default retry behavior covers this if not explicitly disabled.
